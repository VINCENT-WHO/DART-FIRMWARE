# H750 编码与保存流水

适用版本：`2.3.0-writeback`。本次包括JPEG输入重排/输出直写，以及裸机FatFs存储层的64 KiB有界延迟写缓存。相机3 ms固定曝光、RGB识别参数和ROI每侧10像素下界不变。

## 数据流程

```text
DCMI DMA -> 最新YUV帧 -> ROI识别 -> 在原图上画框/文字
    -> JPEG条带重排 -> 硬件JPEG -> 独立JPEG缓冲
    -> 立即释放原始YUV帧槽
    -> FatFs追加AVI -> disk_write复制到64 KiB写回缓存 -> 返回主循环
    -> SD DMA后台写入 -> 等卡就绪 -> 回收对应缓存空间
```

采集DMA、CPU识别/编码和SD DMA可重叠；同一张卡上的文件与扇区写入依然有序串行。没有引入RTOS，也没有从中断调用FatFs。

原始图像每帧150 KiB，不增加整帧副本。JPEG仍为320×240、质量75、4:2:0，输出缓冲容量59392字节。ROI只减少识别计算，录像编码保留完整画面。

## JPEG优化

修改前的2.2.1日志（432帧）记录编码平均7.796 ms，其中像素重排平均5.020 ms，剩余轮询/FIFO搬运/硬件等待平均2.775 ms。这里的数值仅是历史输入的基线，不是新版板端性能结果。

`h750/jpeg_mcu.c` 改为32位读取YUYV并复用同一组输入，合并亮度提取和相邻两行色度平均。输出MCU块序和向下取整规则不变；通过独立空间重建逐字节比较Y/Cb/Cr验证。

`h750/jpeg_hw.c` 将最终JPEG缓冲直接交给HAL，去掉正常输出中的512字节中转复制。HAL轮询长度取4字节倍数；输出恰好填满仍可成功，收到超容量数据则切换scratch排空并返回错误。仍为 `HAL_JPEG_Encode` 轮询，未使用JPEG MDMA。

每次准备JPEG条带前会调用存储服务，推进SD DMA/卡忙状态。服务耗时计入JPEG轮询及搬运细分，不计入像素重排。因而编码与写卡统计存在时间重叠，不能把各自墙钟时间简单相加解释为CPU占用。

## 64 KiB有界扇区写回缓存

实现位于 `h750/diskio_sd.c`，接口和统计在 `h750/fs_test.h`。

- 容量128个512字节扇区，共65536字节，放在SDMMC IDMA可访问的AXI SRAM。当前D-cache保持关闭。
- 每个缓存位置同时保存物理LBA及入队时间；源缓冲来自JPEG或DTCM日志均先复制。`disk_write()` 返回后调用方可以立即复用源内存。
- 所有AVI、DLG及FatFs元数据写入保持提交顺序，同一LBA的重复写不会跳过或乱序。
- 后台把连续物理LBA且环形内存连续的区域合并，每批最多32扇区（16 KiB）。回绕或不连续LBA会切成下一批；同一时刻仅一个SD DMA在运行。
- 传输完成中断只记录完成时间和错误标志。主循环及JPEG条带边界调用 `fs_storage_poll()`，每次最多结算一批并启动下一批，不循环等待卡就绪。
- DMA结束后最多每1 ms查询一次卡状态，观察到 `HAL_SD_CARD_TRANSFER` 才回收缓存。该查询仍是HAL同步状态命令，不能理解为绝对零阻塞；异常硬件命令还受HAL内部超时约束。

状态顺序：`IDLE -> DMA -> CARD -> IDLE`；发生启动/完成/超时/写权限错误则进入锁存的 `ERROR`。5秒为异常超时，不能当作可吸收卡顿的能力指标。

### 有意保留的等待点

1. **缓存满**：等待释放空间后继续接收，不覆盖未写数据，不静默丢录像。超时则结束会话并报告错误。长时间卡忙仍可能拖慢识别、导致相机帧被最新帧策略淘汰。
2. **读取缓存未完整覆盖的范围**：先排空已有写请求，再同步读卡，保证读写一致性。读取范围全命中时直接返回每个LBA最后一次写入的版本，包括仍在DMA或卡忙中的数据。
3. **`CTRL_SYNC`、结束会话**：必须等待全部已接受扇区真正完成，不能只等待DMA发完。

该行为符合 [FatFs disk_write契约](https://elm-chan.org/fsw/ff/doc/dwrite.html)：支持延迟写，但返回后不能继续引用调用方缓冲，完成要求由 `disk_ioctl(CTRL_SYNC)` 发出。所有文件操作仍由原主循环串行执行，未修改 `FF_FS_REENTRANT=0`。

缓存容量只能吸收有限的突发积压。以典型约9.7 KB JPEG、50 fps估算，100 ms新增约49 KB视频数据；64 KiB还需要容纳已有积压、IMU和文件系统扇区，不能保证任意画面或卡的100 ms停顿都不满。长期写入吞吐必须高于长期产生速率。

## 生命周期和数据一致性

文件创建/预分配完成后，通过 `fs_storage_begin()` 开启延迟写；初始化、最终导出和USB读卡仍使用同步路径。

检测结果每帧以16字节RAM记录，最多600条，共9600字节；只有AVI追加提交成功的帧有对应记录，索引与 `DETECT.CSV` 的帧号一致。采集期不逐行格式化/写DETECT，结束后复用8 KiB日志缓冲批量导出，CSV原6列和单位保持不变。

结束顺序：

1. 停相机和IMU，处理截止时间前剩余帧。
2. `f_sync(VIDEO)` 刷出FatFs末尾扇区，刷出DLG日志缓存并同步。
3. `fs_storage_end()` 排空并关闭延迟写模式。
4. 写AVI索引/文件头、截断预分配空间并关闭文件。
5. 导出IMU、DETECT、TIMING和INFO，追加最终状态。
6. 正常排空后卸载文件系统，才把卡交给USB读取。

异步错误锁存后不自动清空队列或重试乱序写入，后续读/写/同步报告失败；未完成会话不会标为正常，卡也不会自动交给USB。串口 `SD CACHE ... error_stage=... hal=...` 提供故障信息；卡自身已无法写入时，不能保证错误日志还能落盘。

## 日志口径

`TIMING.CSV` 保持27列，原 `保存_us` 改为 **`保存提交_us`**，原 `帧完成至保存_us` 改为 **`帧完成至提交_us`**。这两列不再代表物理落盘结束，包含提交开销以及缓存满时的等待。结果码0表示该帧的处理/提交成功，后续异步写入结果以会话FINAL/INFO为准。

最后两列继续为 `JPEG像素重排_us`、`JPEG轮询及搬运_us`。解析脚本应按新列名读取，不应把“提交很快”误认为“SD写入很快”。

`INFO.TXT` 新增写回阶段统计：

| 字段 | 含义 |
| --- | --- |
| 峰值/待写 | 最大缓存占用字节数、当前未完成扇区数，包含在途DMA |
| 提交/完成 | 接受扇区次数、观察到卡就绪后完成的扇区次数，重复写同LBA也计数 |
| DMA批次 | 已启动异步写批次，最多16 KiB每批 |
| 满缓存等待 | 次数、累计和最长等待，正常返回的等待才完成计时 |
| DMA累计/最大 | 启动到DMA完成中断观察的耗时 |
| 卡忙累计/最大 | DMA完成到主循环观察到卡就绪，**包含调度间隔** |
| 最大排队至完成 | 从扇区入队到卡就绪后回收缓存的最大延迟 |
| 最长排空 | 已完成的显式排空调用耗时 |
| 读未命中/命中 | 未命中触发排空次数、完整命中缓存的读取扇区数 |
| 错误阶段 | 0无错误；1权限/状态；2DMA错误；3DMA超时；4卡忙超时；5卡状态错误；6DMA启动失败；7排空超时；8满缓存等待超时；9带未完成请求重置 |

统计只覆盖延迟写阶段；关闭延迟写后的索引、CSV、INFO同步写入不计入这些DMA/队列统计。`IMU.DLG`新增 `STORAGE writeback=65536 chunk=16384 full=wait detcsv=deferred` 配置事件。

## 验证与边界

`python tests/run_tests.py` 编译实际 `diskio_sd.c` 和仓库FatFs，全部操作运行在内存模拟卡上，覆盖：

- 100 ms卡忙期间持续接收入队、满缓存背压、大于64 KiB请求和环形复用。
- 源缓冲返回后被修改、DMA源在途不被覆盖、同LBA最新读、部分读未命中屏障。
- 同步排空、会话重启、微秒计时回绕、分区偏移与LBA溢出保护。
- DMA启动/完成/迟到错误、卡状态错误、DMA/卡忙超时、写保护及USB占用。
- 真实FatFs在内存FAT12镜像上的创建、预分配、两个文件交错的非扇区对齐写入、同步、截断、关闭、重挂载和逐字节回读。

JPEG合成重排测试用 `python tests/verify_hw_jpeg.py`。这些测试与固件编译不等于真实SD卡、JPEG外设及长时间采集验收；本次不使用旧曝光录像测试识别，也不声称实测帧率提升。下一次板测应检查版本、FINAL正常、待写0、提交/完成一致、队列峰值/满等待及JPEG细分。

构建产物的链接布局必须保持AXI SRAM、D2 SRAM和DTCM均不过界。64 KiB缓存已计入AXI，检测结果表及扇区元数据计入DTCM；不把剩余空间当成可无限增加帧缓冲的依据。
